# 현재 MVP vs 실제 서비스 확장 계획

## 요약 표

| 영역 | 현재 MVP | 실제 서비스 |
| --- | --- | --- |
| OCR | mock OCR | OCR API |
| 금융 데이터 | 샘플 거래내역 | 금융 API / 마이데이터 |
| LLM | mock AI 함수 | LLM Agent |
| 저장 방식 | localStorage | DB |
| 사용자 인증 | 없음 | 소셜 로그인 / 금융 인증 |
| 개인화 | 샘플 기준 분석 | 개인별 반복 구매 패턴 |
| 지역상생 | 소비처 유형 기반 | 지역상권 데이터 연동 |

## 영역별 설명

### 1. OCR — mock OCR → OCR API → 전자영수증 → 무입력

**MVP에서 이렇게 구현한 이유**: 머니센스의 차별점은 OCR 정확도가 아니라 "OCR 이후에 무엇을 하는가"이다. 해커톤 MVP에서는 OCR API 비용·지연 없이 핵심 흐름(품목 복원 → 원인분해)을 검증하는 것이 우선이었다. 이미지 업로드 시 mock OCR임을 안내하고 샘플 결과를 사용하며, 인식이 어려운 영수증은 직접 입력으로 유도하는 UX까지 구현했다.

**확장**: `mockParseReceipt()` 내부를 OCR API 호출로 교체. 반환 타입이 유지되므로 UI 변경 불필요.

**입력 허들에 대한 정직한 답**: "사용자가 매번 영수증을 찍을까?"라는 질문에는 "찍지 않게 만든다"가 답이다. 종이 영수증 OCR은 **과도기적 입력 수단**이며, 입력 자동화는 3단계로 간다.

| 단계 | 입력 방식 | 사용자 행동 |
| --- | --- | --- |
| 1단계 (현재 MVP) | 종이 영수증 촬영 + 직접 입력 | 궁금한 소비만 선택적으로 촬영 |
| 2단계 | 네이버·카카오 전자영수증, 대형마트 앱(이마트·홈플러스 등) 모바일 영수증 연동 | 최초 1회 연동 동의 후 자동 수집 |
| 3단계 | 마이데이터 거래내역 + 전자영수증 결합 | 무입력(zero-input) — 거래와 품목이 자동 매칭 |

전자영수증은 이미 구조화된 품목 데이터이므로 OCR 오인식 문제 자체가 사라지고, 머니센스의 매칭·분석 파이프라인은 입력 소스와 무관하게 그대로 동작한다(`Receipt` 타입으로 정규화되기만 하면 된다).

**온보딩 전략 — 전량 입력을 요구하지 않는 설계**: 첫 사용자는 카드·계좌 내역만으로 시작한다. 이 단계에서도 소비처 유형 기반 분석(편의점 비중, 지역가게 비중)은 동작한다. 그러다 "이 4만 원, 뭘 샀더라?"가 궁금한 거래만 영수증으로 선택적으로 보강하면 품목 단위 분석이 열린다. 모든 영수증을 입력해야 가치가 생기는 앱이 아니라, **보강할수록 해상도가 올라가는 앱**이다.

### 2. 금융 데이터 — 샘플 거래내역 → 금융 API / 마이데이터

**MVP에서 이렇게 구현한 이유**: 금융 API 연동은 인증·심사가 필요해 해커톤 기간 내 불가능하다. 대신 실제와 같은 구조(`Transaction` 타입: 날짜·가맹점·금액·결제수단)의 샘플 데이터로 매칭 로직을 검증했고, 사용자가 거래를 직접 추가하는 기능도 넣었다.

**확장**: 마이데이터 API 응답을 `Transaction[]`으로 변환해 주입하면 매칭 이후 파이프라인은 그대로 동작.

### 3. LLM — mock AI 함수 → LLM Agent

**MVP에서 이렇게 구현한 이유**: LLM 호출 없이도 "생활비 온도 계산 → 원인분해 → 플랜 제안"이라는 Agentic workflow 자체를 검증할 수 있도록, 각 단계를 결정적(deterministic) 계산 로직으로 구현했다. 덕분에 데모 수치가 항상 일정해 발표 신뢰성이 높고, 온도 계산 근거("기본 35℃ + 요인별 가산 = 77℃")를 투명하게 보여줄 수 있다.

**확장**: `classifyItem`(품목 분류), `generateActionPlans`(플랜), `generatePresentationSummary`(요약)를 LLM 호출로 교체. 계산 로직은 LLM의 근거 데이터로 유지해 환각을 방지하는 하이브리드 구조를 계획.

### 4. 저장 방식 — localStorage → DB

**MVP에서 이렇게 구현한 이유**: 로그인 없는 데모에서 새로고침에도 데이터가 유지되면 충분하다. 앱 전체 상태를 `AppState` 하나로 직렬화해 localStorage에 저장하므로, 저장 지점이 한 곳이다.

**확장**: 동일한 `AppState` 구조를 서버 DB(사용자별)로 이전. 주간 마감으로 축적되는 비교 기준(`UserBaseline`)이 개인화 데이터의 시작점이 된다.

### 5. 사용자 인증 — 없음 → 소셜 로그인 / 금융 인증

**MVP에서 이렇게 구현한 이유**: 심사위원이 가입 절차 없이 바로 데모를 체험할 수 있어야 한다.

**확장**: 소셜 로그인으로 시작하고, 금융 데이터 연동 시점에 금융 인증(마이데이터 통합인증)을 추가.

### 6. 개인화 — 샘플 기준 분석 → 개인별 반복 구매 패턴

**MVP에서 이렇게 구현한 이유**: 첫 사용자는 비교할 과거 데이터가 없으므로 샘플 이전 기록을 기준으로 시작한다. 다만 구조는 이미 개인화를 향해 있다 — "이번 주 마감"을 누르면 내 기록이 다음 주 비교 기준으로 저장되고, 이전 가격 기록이 없는 품목은 "이번 가격을 기준값으로 저장합니다"로 처리된다.

**확장**: 주 단위를 넘어 품목별 구매 주기·단가 이력을 축적해 온도 가중치와 플랜을 개인화.

### 7. 지역상생 — 소비처 유형 기반 → 지역상권 데이터 연동

**MVP에서 이렇게 구현한 이유**: 소비처 유형(전통시장/동네가게)만으로도 지역상생 소비 비중을 계산하고 "동일 예산 내 전환 제안"까지 보여줄 수 있다.

**확장**: 지역상권 데이터(온누리상품권 가맹점, 지역화폐 가맹점 등)를 연동해 실제 매장 단위 추천과 혜택 연계로 고도화. iM뱅크의 지역 기반과 연결되는 지점.
