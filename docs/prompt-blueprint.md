# LLM 프롬프트 설계도 (Prompt Blueprint)

현재 MVP는 룰 기반 + 결정적 계산 로직으로 Agentic workflow를 검증했다. 이 문서는 **왜 룰 기반만으로는 부족하고 LLM Agent가 필요한지**를 실패 사례로 보이고, 각 Agent를 실제 LLM으로 교체할 때 사용할 프롬프트 구조를 설계한 것이다.

## 핵심 원칙 — "숫자는 코드가, 언어는 LLM이"

| 담당 | 대상 | 이유 |
| --- | --- | --- |
| 결정적 코드 | 생활비 온도, 매칭 점수, 금액 합산, 비중 계산 | 재현 가능·검증 가능해야 하는 수치. LLM 환각이 섞이면 안 됨 |
| LLM | 품목 분류, 상호명 동일성 판단, 원인 문장, 플랜 문장 | 신조어·브랜드·축약어·문맥 등 룰로 열거할 수 없는 언어 영역 |

LLM 출력은 항상 JSON 스키마 검증을 거치고, 검증 실패 시 룰 기반으로 폴백한다. 아래 모든 출력 스키마는 `lib/types.ts`의 타입과 1:1 대응하도록 설계했다 — **이 대응 자체가 "함수 시그니처를 유지한 채 내부만 교체"하는 전략의 증거**다.

## 1. 품목 분류 Agent — `classifyItem`

### 룰 기반의 실패 사례 (현재 MVP 한계)

현재 구현은 키워드 포함 여부(`CATEGORY_RULES`)로 분류한다. 실제 영수증의 품목명 앞에서는 다음과 같이 무너진다.

| 실제 품목명 | 룰 기반 결과 | 문제 | LLM 기대 결과 |
| --- | --- | --- | --- |
| `처음처럼페트360` | `other` (키워드 없음) | 브랜드명만으로는 상품 종류를 알 수 없음 | 주류 → 조정 가능한 소비. 주말 구매 맥락과 결합하면 "홈파티성 지출"로 문맥화 |
| `피코크 감바스 밀키트` | `other` (키워드 없음) | '밀키트'라는 새 상품군을 키워드 목록이 못 따라감 | 간편식(`convenience_meal`) |
| `우유식빵` | `essential` ('우유' 키워드 오탐) | 부분 문자열 매칭의 거짓 양성 — 실제는 빵(간식) | 간식·음료(`snack_drink`) |
| `곰곰 우유 900ml×2 기획` | `essential` (분류는 맞음) | 분류는 되지만 `×2 기획`을 해석하지 못해 **단가 비교가 총액 기준으로 왜곡**됨 | 수량 2 분리 추출 → 단가 기준 가격 비교 정확도 향상 |

키워드 목록을 늘리는 것으로는 해결되지 않는다. 신상품·브랜드·축약어는 매주 생기고, 부분 문자열 매칭은 늘릴수록 거짓 양성이 함께 늘어난다.

### LLM 프롬프트 구조

**system prompt**

```text
너는 한국 영수증 품목 분류기다. 품목명을 보고 아래 카테고리 중 하나로 분류한다.

카테고리 (이 8개 외 값 금지):
essential(필수 식료품) | fresh_food(신선식품) | convenience_meal(간편식)
| snack_drink(간식·음료) | daily_goods(생활용품) | adjustable(조정 가능한 소비)
| local_friendly(지역상생 소비) | other(기타)

규칙:
- 반드시 JSON 한 개만 출력한다. 설명 문장 금지.
- 확신이 없으면 category를 "other"로, confidence를 0.5 미만으로 출력한다.
- 품목명에 수량 표기(×2, 2입, 멀티팩 등)가 있으면 quantity로 분리한다.
- 주류·담배는 adjustable로 분류한다.

출력 JSON 스키마:
{ "category": string, "quantity": number, "confidence": number }
```

**few-shot 예시**

```text
입력: "처음처럼페트360"
출력: { "category": "adjustable", "quantity": 1, "confidence": 0.9 }

입력: "곰곰 우유 900ml×2 기획"
출력: { "category": "essential", "quantity": 2, "confidence": 0.95 }

입력: "우유식빵"
출력: { "category": "snack_drink", "quantity": 1, "confidence": 0.85 }
```

**출력 → 타입 대응**: `category`는 `lib/types.ts`의 `ItemCategory` 유니온과 동일한 값 집합이다. 검증에 실패하거나 `confidence < 0.5`면 룰 기반 `classifyItem()` 결과로 폴백한다.

## 2. 거래내역 매칭 Agent — 상호명 유사도 판단 보조

### 룰 기반의 실패 사례

현재 구현(`isSimilarName`)은 포함 관계 + 공통 글자 비율로 판단한다. 문제는 **카드내역의 법인명과 영수증의 간판명이 아예 다른 경우**다.

| 카드내역 가맹점명 | 영수증 상호명 | 룰 기반 결과 | 실제 |
| --- | --- | --- | --- |
| `(주)코리아세븐` | `세븐일레븐 대구동성로점` | 불일치 (공통 글자 '세븐'뿐) | 같은 가맹점 (코리아세븐 = 세븐일레븐 운영사) |
| `주식회사 우아한형제들` | `배달의민족 주문` | 불일치 (공통 글자 없음) | 같은 결제 (우아한형제들 = 배달의민족 운영사) |
| `(주)이마트24김포한강` | `이마트24 한강신도시점` | 경계선 (글자 비율에 따라 흔들림) | 같은 가맹점 |

법인명↔브랜드명 관계는 문자열 유사도로 계산할 수 없는 **지식의 문제**다.

### LLM 프롬프트 구조

**system prompt**

```text
너는 한국 카드 가맹점명 판독기다. 카드내역의 가맹점명과 영수증의 상호명이
같은 가게에서 발생한 거래인지 판단한다.

규칙:
- 법인명과 브랜드명의 관계(운영사)를 알고 있으면 활용한다.
- 지점명 차이(OO점, 지역명)는 같은 브랜드면 동일 가맹점으로 본다.
- 반드시 JSON 한 개만 출력한다.

출력 JSON 스키마:
{ "sameMerchant": boolean, "confidence": number, "reason": string }
```

**few-shot 예시**

```text
입력: 카드내역 "(주)코리아세븐" / 영수증 "세븐일레븐 대구동성로점"
출력: { "sameMerchant": true, "confidence": 0.95, "reason": "코리아세븐은 세븐일레븐 운영 법인" }

입력: 카드내역 "iM마트 수성점" / 영수증 "샛별시장"
출력: { "sameMerchant": false, "confidence": 0.9, "reason": "마트와 전통시장으로 업종·상호가 다름" }
```

**역할 분리**: 매칭 점수 산식(금액 45·날짜 25·상호 20·결제수단 10)과 판정 기준(80/50점)은 결정적 코드로 유지한다. LLM은 **상호명 20점의 참/거짓 판단만** 보조한다. LLM 실패 시 기존 `isSimilarName()`으로 폴백하므로 매칭 파이프라인은 항상 동작한다.

## 3. 원인분해 Agent — `analyzeCauses`

### 룰 기반의 실패 사례

현재 구현은 계산된 요인을 고정 템플릿 문장에 끼워 넣는다. 정확하지만 **문맥을 결합하지 못한다**.

- "계란 +700원"이라는 사실은 말할 수 있지만, "이번 달 계란값은 전국적으로 오르는 추세라 소비 습관의 문제가 아니다"라는 **위로가 되는 맥락**은 붙이지 못한다.
- 간편식 3회가 모두 야근이 있던 평일 저녁이라는 **패턴 해석**을 하지 못한다.

### LLM 프롬프트 구조

**system prompt**

```text
너는 생활비 분석 리포트 작성자다. 아래 계산 결과(JSON)를 근거로
원인 카드 4장의 설명 문장을 작성한다.

규칙:
- 입력 JSON에 없는 숫자를 만들어내지 않는다. 모든 수치는 입력값을 그대로 인용한다.
- 사용자를 비난하는 표현("낭비", "충동구매")을 쓰지 않는다.
- 각 설명은 2문장 이내의 한국어로 쓴다.
- 반드시 출력 스키마의 JSON만 출력한다.

출력 JSON 스키마 (CauseDetail[]과 동일):
[{ "key": "priceIncrease"|"quantityIncrease"|"storeShift"|"adjustableSpending",
   "title": string, "points": number, "description": string, "details": string[] }]
```

**입력**: `computeFactors()`가 계산한 `TemperatureFactors` 수치 JSON. **points 필드는 입력값을 그대로 복사**하도록 강제한다 — 온도 기여 점수를 LLM이 바꾸지 못하게 하는 환각 방지 장치다.

## 4. 장보기 플랜 Agent — `generateActionPlans`

### 룰 기반의 실패 사례

현재 구현은 데이터 기반 템플릿으로, 대체 가능성은 카테고리 룰(신선식품·기본 식재료 = 전통시장 대체 가능)로 1차 판단한다. 한계는:

- "섬유유연제"를 전통시장에서 사라고 제안하는 실수는 룰로 막았지만, "수입 그릭요거트"처럼 **카테고리는 식품이어도 전통시장에 없는 상품**은 룰이 구분하지 못한다.
- 예산·행사 주기·계절을 결합한 제안("다음 주 장마 예보라 채소는 미리 사두세요")은 템플릿으로 불가능하다.

### LLM 프롬프트 구조

**system prompt**

```text
너는 장보기 플랜 제안자다. 아래 소비 분석 결과(JSON)를 근거로
다음 장보기 액션 플랜 3~4개를 제안한다.

규칙:
- 절약 금액은 입력 JSON의 계산값만 인용한다. 새 금액을 추정하지 않는다.
- 전통시장·동네가게 전환 제안은 substitutable=true인 품목에 대해서만 한다.
- 가격 보장·수익 보장처럼 읽히는 표현을 금지한다.
- 절약과 지역상생을 자연스럽게 연결한다.
- 반드시 출력 스키마의 JSON만 출력한다.

출력 JSON 스키마 (ActionPlan[]과 동일):
[{ "text": string, "savingHint": string?, "isLocal": boolean? }]
```

**few-shot 예시**

```text
입력: { "convenienceMealCount": 3, "convenienceMealTotal": 13200,
        "substitutableItems": [{"name":"계란","amount":7800},{"name":"우유","amount":3200}], ... }
출력: [
  { "text": "편의점 간편식 2회를 장보기 식재료로 대체해보세요.", "savingHint": "약 8,000원 절약 예상" },
  { "text": "계란·우유는 대체 가능한 품목이에요. 동네시장으로 옮기면 지역상생 비중이 올라가요.", "isLocal": true }
]
```

## 폴백 체인 (모든 Agent 공통)

```text
LLM 호출 → (3초 타임아웃 / 네트워크 오류 / API 키 없음) → 룰 기반 폴백
        → 응답 수신 → JSON 스키마 검증 실패 → 룰 기반 폴백
        → 검증 통과 → LLM 결과 사용 (UI에 "AI 분류" 배지 표시)
```

어떤 실패 경로에서도 분석 파이프라인이 멈추지 않는다. 데모·발표 환경에서 네트워크가 끊겨도 룰 기반으로 동일한 흐름이 재현된다.
